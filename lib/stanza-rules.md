# Stanza releases

Applies to any repo whose releases are cut with
[stanza](https://github.com/gitronald/stanza); `version [...]` commits in
`git log` are the tell. Run `stanza guide` for the full release workflow.

## What stanza owns

- Version bumps, release PRs, release merges, tags, and the post-release dev
  cycle go through `stanza release`, never by hand.
- Stable release: `stanza release patch|minor|major -y`, or in two stages:
  `stanza release pr <type> -y`, review the PR, then `stanza release merge -y`.
- Prerelease: `stanza release prerelease -y`.

## Tool-generated commits

stanza writes these commits itself:

| Step | Subject |
|---|---|
| Version bump on `dev` | `version [patch\|minor\|major]: <version>` |
| Prerelease bump, including the post-release dev cycle | `version [prerelease]: <version>` |
| Release merge of the PR into the base branch | `version [release]: v<version> - PR #<N>` |
| Release merge without a PR (`--local` or no remote) | `version [release]: v<version>` |
| Back-merge of the base branch into `dev` (remote mode) | `Merge branch '<base>' into dev` |
| Tag | `v<version>`, lightweight, on the release merge |

The bump commit also carries the README title sync and the CHANGELOG promotion.

- Do not write these subjects by hand, and do not imitate the bracketed
  `version [...]` format in hand-written commits.
- Do not flag them as violations of other commit-message rules, and do not
  amend or rewrite them after the fact.
- Changing one of these forms is a change to stanza, not to the repo.

## Branch and release model

- Alpha versions (`0.1.0a1`) live on `dev`; stable versions are tagged on the
  base branch only.
- Push `dev` before releasing; stanza blocks when local commits are ahead.
- In a repo with a `CHANGELOG.md`, fill `## [Unreleased]` before a stable
  release. stanza promotes it to the new version and blocks when it is empty.
  Prereleases leave the changelog alone.
- Use `-y` for non-interactive runs; add `--json` for machine-readable output.
