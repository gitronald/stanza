# Ship a generated Claude Code rule through a stanza rules command

## Plan

### Motivation

Sessions in other repos keep flagging stanza's release commits as violations of
hand-maintained global git rules. The latest example is the PR merge commit,
which stanza leaves at GitHub's default subject
(`Merge pull request #<N> from <owner>/dev`). The only fix available today is a
one-off edit to one machine's `~/.claude/rules/`, and those edits drift from the
tool as stanza changes: a global rule on the reporting machine still says stanza
writes no changelog prose, which stopped being true when 1.0.0 started promoting
`[Unreleased]` itself.

The `planners` package solves the same problem by shipping its convention prose
inside the package: `planners install` writes a version-stamped copy to
`.claude/rules/planners.md` (global or per-repo), `--check` reports drift, and
it never overwrites a file that lacks its generated marker. Do the same for
stanza. The tool owns the always-on description of its own commit contract, and
every machine with stanza installed gets the same file from the same source.

### What stanza commits today (the contract the rule documents)

Traced from `lib/stanza-release`; the rule prose must match this table.

| Step | Call | Resulting subject |
|---|---|---|
| Version bump on `dev` (full release and `pr` phase) | `git commit -m` | `version [patch\|minor\|major]: <version>` |
| `stanza release prerelease`, and the post-release dev cycle | `git commit -m` | `version [prerelease]: <version>a<N>` |
| PR merge into the base branch (full release and `merge` phase) | `gh pr merge --merge`, no subject flag | GitHub default `Merge pull request #<N> from <owner>/dev`, body `v<version>` |
| Local merge (`--local` or no remote) | `git merge dev -m` | `v<version>` |
| Back-merge of the base branch into `dev` at the start of the next cycle | `git merge <base> --no-ff --no-edit` | git default `Merge branch '<base>' into dev` |
| Tag | `git tag v<version>` | lightweight tag, no commit |
| `stanza init` | none | scaffolds files and pushes only |

The bump commit also carries the README title sync and the CHANGELOG
promotion; neither gets its own commit.

### Scope

In scope:

1. A bundled rule file, `lib/stanza-rules.md`, as the source of truth.
2. A `stanza rules` subcommand: print, `install` (global or `--local`),
   `check`, and `uninstall`.
3. `install.sh` writes the global rule; `uninstall.sh` removes it when it is
   ours.
4. Help text, bash and zsh completions, README, CHANGELOG.
5. `tests/test-rules.sh`, isolated from the real home directory.
6. Decision 2 below: replace the git and GitHub default merge subjects with
   stanza's own `version [release]: ...` form.

Out of scope:

- Writing a per-repo rule from `stanza init`.
- A Claude Code skill holder. `stanza guide` already covers the long-form
  workflow, and repos that want house rules keep their own skill.
- Editing hand-maintained global rules on any particular machine. See
  decision 3; that is a follow-up outside this repo.

### Design

#### 1. Rule prose: `lib/stanza-rules.md`

Short and always-on, under about 60 lines. The guide stays the long-form
document. Sections:

- **What stanza owns.** Version bumps, release PRs, merges, tags, and the dev
  cycle go through `stanza release`, never by hand. One line pointing at
  `stanza guide` for the workflow.
- **Tool-generated commits.** The inventory table above, followed by: do not
  imitate these formats by hand, do not flag them as violations of other commit
  rules, and do not rewrite them after the fact. Changing a form is a change to
  stanza, not to the repo.
- **Branch and release model.** Alpha versions live on `dev`; stable tags land
  on the base branch only. Push `dev` before releasing. Fill `[Unreleased]`
  before a stable release: stanza promotes it and blocks when it is empty. Use
  `-y` for non-interactive runs.
- **Footer.** This file is generated by `stanza rules install`; edit
  `lib/stanza-rules.md` in the stanza repo and reinstall.

No mode placeholders are needed. Unlike planners, stanza is always invoked as
bare `stanza`, so the prose is identical in global and local mode; only the
stamp differs.

#### 2. Subcommand: `lib/stanza-rules`, dispatched from `bin/stanza`

```bash
stanza rules                          # print the rule body (no stamp) to stdout
stanza rules install [--local] [--force]
stanza rules check
stanza rules uninstall [--local]
```

- **Target path.** Global (default) is `~/.claude/rules/stanza.md`. `--local`
  writes `<repo>/.claude/rules/stanza.md`, git-tracked, for repos that want the
  rule to travel with collaborators. Both locations auto-load in Claude Code.
- **Rendered file.** Stamp line, blank line, rule body. Stamp (ASCII only):
  `<!-- generated by stanza <version> (mode=global|local); do not edit;
  regenerate with: stanza rules install --force -->`. The version comes from
  the existing `get_stanza_self_version` in `bin/stanza`, which sourced
  subcommands already inherit.
- **install.** Creates `.claude/rules/` as needed. Refuses to overwrite an
  existing file that lacks the `generated by stanza` marker unless `--force`;
  otherwise rewrites it. Prints `wrote <path>` or `up to date <path>`.
- **check.** Renders fresh and compares against each location that has a file.
  Prints one `ok|drifted|missing` line per location plus a summary; exits
  non-zero unless at least one location exists and every present one is `ok`.
  A stale version stamp counts as drift, which is the intended upgrade signal.
- **uninstall.** Removes the file only when it carries the marker; otherwise
  refuses and says why. Never deletes anything it did not generate.
- **Output contract.** Honors `-h/--help` and `--json` (`command: rules`,
  `action`, `path`, `status`) through the existing `json_set` helpers, so the
  guide's "add `--json` to any command" line stays true.

#### 3. Installer integration

- `install.sh`: a new `install_claude_rule` step after completions. For a user
  install, when `~/.claude` already exists, run `$PREFIX/bin/stanza rules
  install` and report the path; when it does not exist, print the one-line hint
  instead of creating it. `--no-rules` skips the step (mirrors
  `--no-completions`). `--system` installs skip with a hint, because `$HOME`
  under sudo is the wrong home.
- `uninstall.sh`: list and remove `~/.claude/rules/stanza.md` only when it has
  the generated marker.
- `install.sh` already copies `lib/*`, so the prose ships with no other change.

#### 4. Merge subjects

The release merge into the base branch gets a subject in the same bracketed
family as stanza's version commits, so the tool-generated rule covers it.
`version [release]` is reserved for that release merge:

| Merge | Today | New subject |
|---|---|---|
| PR merge (`gh_merge_pr`) | `Merge pull request #<N> from <owner>/dev` | `version [release]: v<version> - PR #<N>` |
| Local merge (`--local` or no remote) | `v<version>` | `version [release]: v<version>` |

- PR merge: pass `--subject "version [release]: v<version> - PR #<N>" --body ""`
  to `gh pr merge`. The version moves into the subject, so the body stays empty.
- Local merge: change the `git merge dev -m` message.
- The back-merge of the base branch into `dev` is not a release, so it keeps
  git's default `Merge branch '<base>' into dev`. The rule documents it as a
  tool-generated form.

#### 5. Docs and completions

- `bin/stanza` help: add the `rules` command line.
- Completions: `rules` with `install check uninstall` and `--local --force`.
- README: a "Claude Code rule" section beside "Guide Command", the project
  structure list, and the release-function list if helpers are added.
- `lib/stanza-guide.md`: one line in "Rules of the road" pointing at
  `stanza rules`.
- CHANGELOG `[Unreleased]`: Added (`stanza rules`, installer step), Changed
  (merge subject).

#### 6. Tests: `tests/test-rules.sh`

Run every case with `HOME` set to a fresh temp directory so nothing touches the
real `~/.claude`. Cases:

- `stanza rules` prints the body with no stamp line.
- `install` writes the stamped file; a second `install` is idempotent.
- `check` reports `ok`; after a hand edit, `drifted` with exit 1; after removal,
  `missing` with exit 1.
- `install` refuses a pre-existing unstamped file; `--force` overwrites it.
- `--local` writes into the repo's `.claude/rules/`; `check` reports both
  locations.
- `uninstall` removes a generated file and refuses an unstamped one.
- `--json` output carries `command`, `action`, `path`, and `status`.

For the merge subjects, extend the existing local-mode release tests to check
the local merge subject. The PR merge subject has no unit test,
because those suites never call `gh`. Verify it on the first real release after
this merges and record the resulting subject in the Log.

### Decisions to confirm

1. **Base branch.** Branch the worktree off `dev`. Recommended; `dev` and the
   base branch are identical at time of writing, and all active development
   lands on `dev`.
2. **Merge subject.** Adopt stanza's own `version [release]: ...` form for the
   release merge, PR or local (design section 4). Reserve it for releases: the
   back-merge into `dev` keeps git's default. Decided. `[release]` rather than
   `[merge]` because the version tag points at this commit, so it is the release
   itself; `PR #<N>` rather than a bare `#<N>` so the reference is unambiguous.
   The complaints came from GitHub's default subject, which reads like a hand-written merge that breaks the git
   rules. A bracketed stanza subject is recognizably tool-generated, sits in the
   same family as `version [patch]` and `version [prerelease]`, and keeps the
   account handle out of base-branch history. This replaces the earlier
   `merge: PR #<N> - dev` proposal, which would have imitated a hand-written
   convention from inside the tool.
3. **Hand-maintained global rules.** After the generated rule is installed on a
   machine, any global rule there that restates stanza specifics (the merge
   subject clause, the changelog claim) should be trimmed to defer to
   `~/.claude/rules/stanza.md`. This is machine-local and outside the repo, so it
   is a follow-up, not a deliverable of this plan.
4. **Installer behavior.** `install.sh` writes the rule automatically when
   `~/.claude` exists, and only prints a hint otherwise. Recommended over
   always creating `~/.claude/` for users who do not run Claude Code.

### Implementation order

1. `lib/stanza-rules.md` prose.
2. `lib/stanza-rules`, `bin/stanza` dispatch, and help text.
3. `tests/test-rules.sh`; run it and the existing suites.
4. `install.sh` and `uninstall.sh`.
5. Completions, README, guide line, CHANGELOG.
6. Merge subject change and matching rule text (decision 2).
7. Verify end to end: `./install.sh --prefix=<tmp>` with `HOME=<tmp>` writes
   `<tmp>/.claude/rules/stanza.md`, `stanza rules check` exits 0, and
   `uninstall.sh` removes it. Open a fresh Claude Code session and confirm the
   rule appears among the auto-loaded rules.

Commit in logical chunks as each step lands.

## Retrospective

- The scope held: rule prose, subcommand, installer steps, docs, and the merge
  subject all landed as planned. The surprises came from two defaults of the
  environment, not from the plan itself. Local merges fast-forwarded, and
  `set -e` doesn't fire inside `&&` lists.
- Changing a merge from fast-forward to `--no-ff` changes what the other branch
  can reach. The back-merge step had depended on the fast-forward without
  saying so. When a history-shape invariant changes, re-check every step that
  reads that history.
- Marker checks need anchoring. A marker phrase that is plain English will
  turn up in hand-written files, so a "never touch what we didn't write"
  guarantee has to key on the exact stamp position, not a substring.
- The planned "no unit test for the PR merge subject" was too pessimistic.
  Making the gh mock honor `--subject` turned it into an asserted contract. It
  is worth checking whether a mock can carry a behavior before deferring it to
  a manual check.
- Next time, keep a completion test alongside any subcommand with
  action-specific flags. The bash completion was testable with a stub
  `_init_completion` all along.
